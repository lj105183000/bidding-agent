# 并行开发协作

> 本文件是多个 Claude 子 Agent 并行开发本仓库的**唯一流程事实源**。
> 机器可读的所有权清单见 `.claude/parallel/lanes.json`；两者不一致时以 `lanes.json` 为准，并立即修正本文件。
>
> 本流程只改变**开发方式**，不改变产品运行时架构：`BiddingAgent`、工具注册表、SSE 链路均保持原样。

---

## 1. 目的与适用边界

### 1.1 目标

- 多个 lane 在独立 worktree / 分支上并行修改互不重叠的模块；
- 用**冻结契约 + targeted 测试 + 集成 owner 串行合并**控制契约漂移；
- 用**共享资源预约表**避免并发写坏 `trend.jsonl`、fixtures、真实库、`dist` 等。

### 1.2 硬规则

1. **任一时刻最多 3 个写 lane 并发**。集成 owner 不算 lane。
2. 每个 lane 一个独立 worktree，一个 `feat/parallel/<lane>` 分支，一个写者。
3. 只有 integrator 合并 PR、改 `api/server.py`、改文档、改 lockfiles、写共享评测资源。
4. lane 只跑 targeted 测试；全量测试、前端 build、离线门禁只在集成窗口跑。
5. 冻结文件/共享资源的变更走 **CCR（Contract Change Request）**，不允许 lane 单方面修改。

### 1.3 适合并行

- `frontend` 叶子页面/组件（不改变 `lib/api.ts` 既有函数签名与字段）；
- `datahub` / `eval_runs` / `eval_online` / `eval_offline` 等自洽模块；
- `rag` 离线可验证的改动；
- `services` 两条独立链（tender 链 / analysis 链）；
- `clients` / `mcp` 等平台模块；
- `batch/` 独立脚本。

### 1.4 只能串行或单 owner

| 内容 | 处理方式 |
|---|---|
| `api/server.py`（3411 行 / 85 端点） | integrator 单写 |
| `src/config.py`、`src/logging_config.py`、`src/agent/constants.py`、`src/constants/**` | contracts-platform 单写 |
| `src/agent/__init__.py`、`src/rag/__init__.py`、lockfiles、文档、共享评测数据 | integrator 单写 |
| `src/agent/core.py` + `react_loop.py` + `src/tools/**` + `database/graph_data.py` | agent-core 单写者，不拆给两个 agent |
| `frontend/src/lib/api.ts` 的既有签名/字段、`Chat.tsx` | 同一个 frontend lane 顺序修改 |
| `eval/trend.jsonl`、`baseline.json`、`fixtures/**`、`online_samples.jsonl` | integrator 串行写 |

### 1.5 不适用

- 需要 `ingest` / `pg --force` / `graph --clear` 的改动；
- 需要同时改 API + service + 前端的全栈特性（拆成多个波次）；
- 需要改 eval 阈值 / fixture / 基线的改动（integrator 串行）；
- 产品运行时多 Agent 编排（Phase 1 已落地；属于 CCR 级变更，`src/agent/core.py` / `react_loop.py` / `api/server.py` 仍由 integrator 单写，新包 `src/agent/orchestration/**` 归 agent-core lane）。

## 4. 冻结契约与 CCR

### 4.1 冻结契约清单

| 面 | 冻结内容 | 守护方式 |
|---|---|---|
| Agent 公共导入 | `src.agent.__all__` 的 11 个导出 | `tests/test_parallel_contracts.py` |
| RAG 公共导入 | `src.rag.__all__` 的关键导出、`RAGPipeline.search` 签名与结果键 | 同上 |
| 工具注册 | `TOOL_EXECUTORS` 键集合 = `BASE_TOOL_NAMES ∪ WEB_TOOL_NAMES`；执行器签名 `(arguments, question="") -> (text, sources)` | 同上 |
| 工具结果 | `ToolResult.to_dict()` 恒为 `success + data/results + error` | 同上 |
| SSE `done` 帧 | `sources / web_sources / tool_name / elapsed_ms / phase_times`；`tool_name` 必须是单字符串 | 同上 |
| 多 Agent done 字段 | `orchestration / agent_trace / agent_timings` 为 additive；多 Agent 下 `tool_name` 为 primary specialist 的最后一个成功工具 | `test_parallel_contracts.py` + `test_multi_agent_graph.py` |
| 会话落库 | `PersistedMessage`：`id / role / content / sources / toolName / imageAnalyses` | `test_sse_events.py` + 前端类型 |
| API | 路径、请求字段、响应字段、错误码 | integrator 单写 + `test_api_server.py` |
| 评测趋势 | `eval/trend.jsonl` schema、fixture SHA 校验 | `eval/trend.py` + retrieval gate |
| 配置 | `.env` 键名与 `Settings` 字段 | `开发文档.md` §2.3 |

### 4.2 CCR 流程

lane 需要修改冻结项时：

1. 在 worktree 写 `.parallel/BLOCKED.md`：改什么、为什么、消费方、迁移方案、需要更新的测试；
2. 停止修改该文件，不自行绕路；
3. integrator 评估：
   - 批准 → integrator 从 main 开 `feat/contract/<name>`，更新冻结文件 + `test_parallel_contracts.py` + 文档；
   - 合并后 bump `contract_version`，打新 tag `parallel-base-vN`；
   - 所有 lane `git merge origin/main` 后继续；
   - 拒绝 → lane 调整方案。

> 不是用例失败；CI（Linux）不受影响。

## 8. 合并顺序与队列

每个波次固定顺序：

1. 契约/平台 PR（如有）；
2. API 骨架 PR（跨栈特性时 integrator 先合）；
3. `data-eval-platform` PR；
4. `rag` PR（离线门禁通过后合）；
5. `services-tender` / `services-analysis` PR（按 API 依赖排序）；
6. `agent-core` PR（后端耦合最高，放最后）；
7. `frontend` PR（API 稳定后合）；
8. 文档同步 PR；
9. trend / baseline 更新 PR（只有确实需要时）。

队列规则：

- 只有 integrator 执行 `gh pr merge`；
- 一次只合一个 PR；
- 每合一个，剩余 lane `git merge origin/main`（不 force、不 rebase 已推送分支），重跑 targeted + 契约测试；
- Squash merge；PR 标题遵守 `类型(模块): 中文描述`；
- 不堆叠 PR：B 依赖 A 时，等 A 合入 main 后 B 再 merge main；
- main 被合坏时用 revert commit 回滚，不在 main 上直接修复后强推。

## 9. handoff / 失败回滚

lane 完成时必须写 `.parallel/PROGRESS.md`，并在 PR body 附 handoff JSON：

```json
{
  "lane": "rag",
  "base_tag": "parallel-base-v1",
  "commits": ["..."],
  "files": ["..."],
  "tests": ["命令 + 结果"],
  "contract_changes": [],
  "blocked": [],
  "next_steps": []
}
```

失败处理：

- targeted 测试红：lane 自己修，不带病 handoff；
- 需要冻结文件/跨 lane 依赖：写 `.parallel/BLOCKED.md` 并停止；
- 合并冲突：lane `git merge origin/main` 本地解决 → commit → push；绝不 `--force`；
- main 回滚：integrator 用 revert commit，通知所有 lane 重新同步。

## 11. 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 在 lane 里跑 `uv sync` / `uv lock` | 争抢 uv 环境锁，依赖漂移 | 用共享 `.venv`，依赖变更走 integrator |
| lane 跑 `--save` / `--gate` 写真实 trend | 并发追加丢记录 | 用 `.parallel/trend-<lane>.jsonl` |
| lane 复制 `.env` | 真实库测试执行，Postgres 计数抖动 | worktree 不放 `.env` |
| lane 跑 `npm run build` | 并发写 `frontend/dist` | 只跑 `npm run test` / `npx tsc -b` |
| lane 改 `api/server.py` / `src/agent/__init__.py` | 契约漂移、合并冲突 | 走 CCR，integrator 单写 |
| lane 改 `CLAUDE.md` / docs | 多 lane 文本冲突 | 写 doc-delta，integrator 统一应用 |
| lane 跑 `-m integration` / 真实库 | 并发写真实数据 | 只在 integrator 串行窗口跑 |
| 同时开 4+ lane | 集成吞吐与共享资源超载 | 硬上限 3 |
| 用 `--force` 覆盖他人分支 | 丢提交 | pull → 解决 → commit → push |
